## 1. 課稅與稅額

### 1.1 `TaxType` 課稅類別

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `1` | 應稅（一般應稅） | 開立發票、註銷重開、上傳開立發票、查詢發票（明細回傳） | i100 §7 §12；i200 §7 §17 §18 §24；i301 §13 |
| `2` | 零稅率 | 同上 | 同上 |
| `3` | 免稅 | 同上 | 同上 |
| `4` | 應稅（特種稅率） | 同上 | 同上 |
| `9` | 混合應稅與免稅或零稅率 | 開立發票、註銷重開（**限收銀機發票無法分辨時使用，且需通過申請核可**） | i100 §7 §12 |

**與 `InvType` 的連動規則**（i100 §7 原文）：

| `InvType` | 允許的 `TaxType` |
|:---:|---|
| `07` 一般稅額 | `1` `2` `3` `9`　⚠️ 但 **i100 §12 註銷重開** 章節寫的是 `1` `2` `9`，**未含 `3`（免稅）** |
| `08` 特種稅額 | `3` `4` |

> ⚠️ **原文跨章矛盾（已回原文逐行確認）**：
> `Issue`（i100 §7，原文第 392 行）與 `DelayIssue`（i100 §7，原文第 575 行）都寫「`InvType=07` 請填入 **1、2、3 或 9**」，
> 但 `VoidWithReIssue`（i100 §12，原文第 1428 行）只寫「**1、2 或 9**」，少了 `3`（免稅）。
> 三處 reference 均逐字照抄未修改。**若你照註銷重開那段實作，會誤以為免稅發票不能註銷重開。**
> 免稅發票需註銷重開時，請先向歐付寶確認 `TaxType=3` 是否受理。
>
> i200 §7 的寫法是「`InvType=07` 帶 1/2/3；`InvType=08` 帶 3/4」，**沒有 `9`**。B2B 不支援混稅。
> 為什麼要盯緊：`TaxType` 決定 `SalesAmount` / `TaxAmount` / `TotalAmount` 的計算方式與 `SpecialTaxType` 是否必填，填錯不是拒絕開立就是金額對不上財政部。

### 1.2 `ItemTaxType` 商品課稅別

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `1` | 應稅 | 開立發票、開立折讓、註銷重開、查詢發票明細、查詢折讓明細、上傳開立發票 | i100 §7 §8 §12 §13 §14；i301 §13 |
| `2` | 零稅率 | 同上 | 同上 |
| `3` | 免稅 | 同上 | 同上 |

**規則**（i100 §7 原文）：預設為空字串；**當 `TaxType = 9` 時此欄位不可為空**。混合稅率時需含二筆以上明細，且至少一筆為應稅、至少一筆為免稅或零稅率——即混稅發票只能是 **1. 應稅＋免稅** 或 **2. 應稅＋零稅率**，**免稅和零稅率不能同時開立**。

### 1.3 `SpecialTaxType` 特種稅額類別

| 值 | 意義 | 稅率 | 來源 |
|:---:|---|:---:|---|
| `0` | `TaxType` 為 1/2/9 時，系統自動帶入 | — | i100 §7 §12；i301 §13 |
| `1` | 酒家及有陪侍服務之茶室、咖啡廳、酒吧 | **25%** | i100 §7；i200 §7 |
| `2` | 夜總會、有娛樂節目之餐飲店 | **15%** | 同上 |
| `3` | 銀行業、保險業、信託投資業、證券業、期貨業、票券業及典當業之**專屬本業收入**（不含銀行業、保險業經營銀行、保險本業收入） | **2%** | 同上 |
| `4` | 保險業之**再保費收入** | **1%** | 同上 |
| `5` | 銀行業、保險業、信託投資業、證券業、期貨業、票券業及典當業之**非專屬本業收入** | **5%** | 同上 |
| `6` | 銀行業、保險業經營銀行、保險本業收入（適用於**民國 103 年 07 月以後**銷售額） | **5%** | 同上 |
| `7` | 銀行業、保險業經營銀行、保險本業收入（適用於**民國 103 年 06 月以前**銷售額） | **5%** | 同上 |
| `8` | 空白為免稅或非銷項特種稅額之資料 | — | 同上 |

**必填規則**：

| `TaxType` | `SpecialTaxType` |
|:---:|---|
| `1` / `2` / `9` | 系統自動帶 `0`（i301 明寫「請帶入【0】」） |
| `3` 免稅 | **必填 `8`** |
| `4` 特種應稅 | **必填，可填 `1`～`8`** |

> 為什麼容易錯：`6` 和 `7` 稅率同樣是 5%，差別只在**銷售額所屬期間**（民國 103 年 7 月為界）。選錯不會被擋，但申報時會對不上。

|:---:|---|---|
| `71` | 第一款　外銷貨物（**預設值**） | i100 §7 §12 §13；i200 §7 §17 §18；i301 §13 |
| `72` | 第二款　與外銷有關之勞務，或在國內提供而在國外使用之勞務 | 同上 |
| `73` | 第三款　依法設立之免稅商店銷售與過境或出境旅客之貨物 | 同上 |
| `74` | 第四款　銷售與保稅區營業人供營運之貨物或勞務 | 同上 |
| `75` | 第五款　國際間之運輸。但外國運輸事業在中華民國境內經營國際運輸業務者，應以各該國對中華民國國際運輸事業予以相等待遇或免徵類似稅捐者為限 | 同上 |
| `76` | 第六款　國際運輸用之船舶、航空器及遠洋漁船 | 同上 |

**必填規則**（i100 §7 原文）：當 `TaxType = 2`（零稅率）或 `9`（混合應稅與零稅率）時為必填；若廠商回傳時無帶值，**預設 `71`**。

> ⏰ i200 / i301 額外註明：**自民國 115 年 1 月 1 日起**，`TaxType=2`（i301 另含 `9`）時此欄位必填，或必須在廠商後台設定以便程式抓取，**否則將會開立失敗**。這是 2026 年起會突然開始踩到的雷。
> 此欄位是 i100 V1.5.0（2025/08/28）新增的，舊版串接程式很可能沒有這個欄位。

## 2. 字軌與配號

### 2.1 `InvType` 字軌類別

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `07` | 一般稅額發票（一般稅額計算之電子發票） | 查詢財政部配號結果、字軌與配號設定、開立發票、註銷重開、查詢字軌、查詢空白未使用發票、取得自動配發發票字軌號碼、上傳開立發票 | i100 §4 §5 §7 §12 §17 §27；i200 §5 §7 §17 §28；i301 §6 §9 §11 §13 §15 |

### 2.4 ⚠️ `InvoiceStatus` 發票字軌狀態 — **兩套定義**

**定義 A：設定字軌號碼狀態時（0/1/2）**

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `0` | 停用 | 設定字軌號碼狀態 | i100 §6；i200 §6；i301 §10 |
| `1` | **暫停** | 同上 | 同上 |
| `2` | **啟用** | 同上 | 同上 |

補充（原文）：如狀態設定為停用，該字軌區間**無法上傳發票**。
i200 §2 另註明：字軌通過審核後須啟用；**啟用後可暫停或停用，但停用後無法再度啟用**。→ `0` 是不可逆操作。

**定義 B：離線取得發票字軌號碼時（1/2）**

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `1` | **啟用** | 取得發票字軌號碼 | i301 §12 |
| `2` | **備用字軌** | 同上 | 同上 |

> 🚨 **同一個欄位名，`1` 在 A 是「暫停」、在 B 是「啟用」；`2` 在 A 是「啟用」、在 B 是「備用字軌」。** 詳見 [§10](#10-同名不同義的陷阱)。

> ℹ️ **i301（離線）自己也完整列出了 `1`~`8` 的載具類別**（i301 §13 上傳開立發票，原文第 887 行），

> `V1.2.0（2025-05-12）調整非共通性載具_顯碼/隱碼`——非共通性載具的顯碼／隱碼規則是 i301 自己維護的內容。
> 因此上表的 `1`~`8` 同時適用於 i100 §7、i301 §13；逐欄位規格見
> [`offline-api-reference.md`](offline-api-reference.md)。

**`CarrierNum`（載具編號）與 `CarrierNum2`（第二載具編號）的填法**（i100 §7 原文整理）：

| `CarrierType` | `CarrierNum` | `CarrierNum2` |
|:---:|---|---|
| `""` | 空字串 | 不帶 |
| `1` | **空字串**，系統自動帶入（客戶 Email 或手機號碼擇一，**Email 優先**） | 不帶 |
| `2` | 固定長度 **16**：2 碼大寫英文 + 14 碼數字 | 不帶 |
| `3` | 固定長度 **8**：第 1 碼為 `/`，其餘 7 碼由數字 `0-9`、大寫英文 `A-Z` 與 `+` `-` `.` 這 **39 個字元**組成 | 不帶 |
| `4`～`7` | **必填**：實體卡片的**隱碼 id**（不檢核正確性） | **必填**：實體卡片的**顯碼 id**（不檢核正確性） |
| `8` | **必填**：信用卡加密卡號 | **必填**：刷卡日期（民國年月日共 7 碼）+ 刷卡交易金額（10 碼，不足位**左補 0**） |

**顯碼／隱碼的關鍵注意事項**（原文）：
- `CarrierType=4~8` 時，`CarrierNum` 代表**隱碼**、`CarrierNum2` 代表**顯碼**。
- 英文、數字、符號**僅接受半形字元**；`CarrierNum2` 格式錯誤**會造成開立失敗**。
- 當 `CarrierType` 為 `1`、`2`、`3` 時，**請勿填入 `CarrierNum2`，以免被系統阻擋**。
- 取得 `4~7` 卡片隱碼（內碼）需設備配備能讀取卡片內碼的讀卡機。
- 查詢發票 API 在 `CarrierType=4~8` 時，**因資安考量不會回傳隱碼 id**（回傳的是顯碼，見 §6 的 `IIS_Carrier_Num`）。
- 手機條碼載具**會進行格式檢核**；使用前請先呼叫「手機條碼驗證」API（i100 §20）。

**與 `Print` / `CustomerIdentifier` 的連動**（i100 §7 原文）：
- 當 `Print=1`（要列印）時，`CarrierType` 請帶**空字串**。
- 當 `Print=0`（不列印）且 `CustomerIdentifier`（統一編號）有值時，`CarrierType` **不可帶空字串**。

## 7. B2B 專屬

### 7.1 `ExchangeMode` 上傳模式（存證／交換）

| 值 | 意義 | 出現在哪些 API | 來源 |
|:---:|---|---|---|
| `0` | **存證** | 交易對象維護、查詢發票、查詢發票確認 | i200 §3 §18 §19 |
| `1` | **交換** | 同上 | 同上 |

**原文說明**：
- **存證**：歐付寶會將您的發票資料上傳至財政部，**僅適用於銷項發票**。※加值中心**無法接收**其他營業人開立給您的電子發票。
- **交換**：歐付寶會將發票資料上傳至財政部發票傳輸軟體，供對方營業人確認及接收。※**請務必先至財政部平台設定由歐付寶接收**。

> 為什麼要盯緊：`ExchangeMode` 決定了 `InvoiceTag`（§4.1）可用範圍、`ExchangeStatus` 的語意（見下）、以及是否收得到進項發票。這是 B2B 串接最上游的一個決策，設錯後面全部連鎖錯。
> ⚠️ 記憶點：**`0` 是存證、`1` 是交換**。i200 §3 有一處寫成「`0: 存證  1. 交換`」（用了句點），別看成 `1.` 是條列編號。

## 10. 同名不同義的陷阱

**這一節是本文件存在的主要理由。** 以下欄位在不同文件／不同章節／甚至同一個 request body 的不同區塊，定義完全不同。**混用不會噴錯，只會靜默算錯。**

### 10.1 ⚠️ `InvoiceStatus` — 三份文件、兩套值

| 章節 | 值域 | 定義 |
|---|---|---|
| **i100 §6** 設定字軌號碼狀態 | `0` `1` `2` | `0`=停用、`1`=**暫停**、`2`=**啟用** |
| **i200 §6** 設定字軌號碼狀態 | `0` `1` `2` | 同上 |
| **i301 §10** 設定字軌號碼狀態 | `0` `1` `2` | 同上 |
| **i301 §12** 取得發票字軌號碼 | `1` `2` | `1`=**啟用**、`2`=**備用字軌** |

**風險**：離線串接同時會用到 §10 和 §12。若把兩處共用同一個 enum：
- 在 §12 拿到 `1`（啟用）的字軌，拿去 §10 當作狀態送出 → 變成**暫停**該字軌。
- 在 §12 拿到 `2`（備用字軌），拿去 §10 送出 → 變成**啟用**。

兩個方向都是「送得出去、回 `RtnCode=1`、結果完全相反」。

**做法**：定義成兩個型別，名字寫清楚用途，例如 `InvoiceTrackStatusSetting`（0/1/2）與 `InvoiceTrackAllocationKind`（1/2），不要叫 `InvoiceStatus`。

### 10.2 ⚠️ `UseStatus` vs `InvoiceStatus` — 別當成同一件事

| 欄位 | 章節 | 值域 | 定義 |
|---|---|---|---|
| `UseStatus` | i100 §17 / i200 §28 / **i301 §15** 查詢字軌 | `0`～`6` | `0`=全部（查詢條件）、`1`=未啟用、`2`=使用中、`3`=已停用、`4`=暫停中、`5`=待審核、`6`=審核不通過 |
| `InvoiceStatus` | 設定字軌號碼狀態 | `0`～`2` | 見 §10.1 |

**風險**：兩者都在描述「字軌的狀態」，但一個是**查詢回傳的生命週期狀態（6 種）**、一個是**設定用的動作值（3 種）**，且**數字撞號但意義不同**：

| 數值 | `UseStatus` | `InvoiceStatus`（設定） |
|:---:|---|---|
| `0` | 全部（查詢萬用值） | **停用** |
| `1` | 未啟用 | **暫停** |
| `2` | 使用中 | **啟用** |

拿查詢回來的 `UseStatus=2`（使用中）直接餵給設定 API 當 `InvoiceStatus`，剛好也是 `2`（啟用），會**碰巧正確**——這比錯更危險，因為它會讓你以為兩者通用，直到某天拿到 `UseStatus=1`（未啟用）送過去變成「暫停」。

### 10.3 ⚠️ `InvoiceCategory` — 同一份 i200 文件內就兩套

| 章節 | 值域 | 定義 |
|---|---|---|
| i100 §5 §17 §27 | `1` | B2C（固定值） |
| **i200 §5 §28** | `2` | B2B（固定值） |
| **i200 §18–§23** 各查詢 API | `0` `1` | `0`=**銷項發票**、`1`=**進項發票** |
| i301 §9 §15 | `4` | 離線發票（固定值） |

**風險**：B2B 開發者習慣在共用 config 裡寫 `INVOICE_CATEGORY = 2`，然後查詢 API 也帶 `2` → 超出定義；或反過來，在字軌章節帶 `0`/`1` → 查無資料。i100 §17 原文就明寫「**請固定填寫為 1，否則會查無資料**」。

### 10.4 ⚠️ `InvoiceTag` — B2C 字母 vs B2B 數字

| 文件 | 值域 | 型態 |
|---|---|---|
| i100 §18 | `I` `II` `A` `AI` `AW` | `String(2)` |
| i200 §4 | `1`～`10` | `String(1)`（但 `10` 是兩碼，官方型態標示與實際不符） |

**風險**：同時串 B2C 與 B2B 的系統若共用一個「通知類型」enum，會把 `A`（B2C 折讓開立）送進 B2B、或把 `1`（B2B 發票開立）送進 B2C。B2C 的 `I` 與 B2B 的 `1` 都代表「發票開立」，但字面不同，複製貼上時特別容易錯。

### 10.5 ⚠️ `NotifySwitch` / `NotifyType` — 同一個 request body 裡兩套

i100 §23 取得發票通知開關 / §24 設定發票通知開關，`Data` 內同時有 `CostomerSetting` 與 `SelfSetting` 兩個陣列：

| 區塊 | `NotifyType` | `NotifySwitch` |
|---|---|---|
| `CostomerSetting`（給消費者） | `1`～`6` | `0`～`5`（含通知管道選擇） |
| `SelfSetting`（給自己） | `1`～**`8`** | `0` / `1`（**只有開關**） |

**風險**：寫一個 `buildNotifySetting()` 兩邊共用 → 對 `SelfSetting` 送 `NotifySwitch=3`（消費者定義的「優先 Email」）超出定義；或對 `CostomerSetting` 送 `NotifyType=7`（開立失敗）——消費者根本沒有這個通知類型。
**額外提醒**：官方欄位名拼寫是 `CostomerSetting`（少了一個 `u`），照抄，不要「修正」成 `CustomerSetting`。

### 10.6 ⚠️ 上傳狀態家族 — B2C 兩值、B2B 三值

| 欄位 | 文件 | 值域 |
|---|---|---|
| `IIS_Upload_Status` / `IA_Upload_Status` / `II_Upload_Status` / `AI_Upload_Status` | i100 §13–§16 | `0` 未上傳、`1` 已上傳 |
| `UploadStatus` | i100 §27 | `0` 未上傳、`1` 已上傳 |
| **`Upload_Status`** | **i200 §18–§27** | `0` 未上傳、`1` 已上傳、**`2` 上傳失敗** |

**風險**：B2C 的邏輯是「`0` = 還沒上傳，稍後再查」。把同一段邏輯套到 B2B，`2`（上傳失敗）會被歸到 `!= 1` 的分支當成「還在處理」，於是**無限輪詢一張永遠不會成功的發票**，而且不會有任何錯誤訊息。

### 10.7 ⚠️ `Issue_Status` 的 `0` — B2B 是「退回」，B2C 是「註銷」

| 欄位 | 文件 | `1` | `0` |
|---|---|---|---|
| `IIS_Issue_Status` | i100 §13 | 發票開立 | **發票註銷** |
| `Issue_Status` | i200 §18 §19 | 發票開立 | **發票退回** |

**風險**：「註銷」（可註銷重開、號碼保留）與「退回」（B2B 買方退回賣方的發票）是完全不同的業務事件，後續處理流程不同。共用一個顯示字串會誤導客服與帳務。

### 10.8 ⚠️ `Action`（B2B, 字串）vs `ActionType`（離線, 數字）

| 欄位 | 文件 | 值域 | 型態 |
|---|---|---|---|
| `Action` | i200 §3 交易對象維護 | `Add` / `Update` / `Delete` | `String(10)` |
| `ActionType` | i301 §7 管理發票機台 | `1` / `2` / `3` | `Int` |

功能等價（新增/修改/刪除），型態與欄位名都不同。抽象成一個共用的 `CrudAction` 型別時，記得在序列化層分開處理。

### 10.9 ⚠️ `CarrierType`（送出 1–8）vs `IIS_Carrier_Type`（回傳 1–3）

| 欄位 | 值域 |
|---|---|
| `CarrierType`（開立時送出） | `""` `1` `2` `3` `4` `5` `6` `7` `8` |
| `IIS_Carrier_Type`（查詢發票明細回傳） | `1` `2` `3` |

**風險**：以為送出去什麼就查得回什麼。實際上 i100 §13 只定義了 `1`～`3`；且原文明說 `4~8` 時 `IIS_Carrier_Num` 回的是**顯碼**不是隱碼。做「開立後回查驗證」的對帳程式時，不能拿 `CarrierNum` 直接比對 `IIS_Carrier_Num`。

### 10.10 ⚠️ `RtnCode=1` 不是所有 API 的成功碼

| API | 成功碼 |
|---|---|
| 絕大多數 API | `1` |
| **開立發票**（`DelayDay = 0`） | **`4000004`** |
| **開立發票**（`DelayDay > 0`，延後開立） | **`4000003`** |

**風險**：這是全套文件裡最貴的一個坑。`if (RtnCode !== 1) retry()` 會把「開立成功」判成失敗然後重送 → **同一筆訂單開出兩張發票**。詳見 [`error-handling.md`](./error-handling.md) 的重試策略。

## 11. 給 AI 助手／程式碼產生器的提醒

1. **不要補值。** 本文件沒有列的值就是官方沒定義。看到 `1` `2` `4` 中間跳過 `3`（`InvoiceCategory`），那就是真的沒有 `3`。
2. **不要合併同名欄位。** 上面 §10 列了 10 組陷阱，每一組都要生成獨立型別。
3. **字串型的數字要保留前導零。** `InvType` 是 `"07"` 不是 `7`；`ZeroTaxRateReason` 是 `"71"`。
4. **空值有意義。** `CarrierType=""`（無載具）、`IIS_Award_Flag=""`（不可對獎）、`ExchangeStatus=""`（未設定），三者都不等於 `0`。
5. **官方拼寫照抄**：`CostomerSetting`、`vat`、`type` —— 這些不是筆誤要修正的地方，是 API 契約。
6. **錯誤碼不要編。** 除了本文件 §5.2 列的四個，官方未公開完整錯誤碼表，見 [`error-handling.md`](./error-handling.md)。
