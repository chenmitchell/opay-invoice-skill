# /opay-doctor —— 串接健檢

使用者說「打不通」「一直失敗」「不知道哪裡錯」的時候跑這個。
**由近而遠、由便宜到昂貴**依序檢查，不要一開始就叫他去打 API。

## 檢查 1：加密實作對不對（不需要網路，最便宜）

```bash
python3 test-vectors/verify.py
node test-vectors/verify-node.js
```

四組向量必須全過。**任何一組不過，後面的檢查都不用做了** ——
加密錯了，所有 API 都會在 `TransCode` 就失敗，而錯誤訊息不會告訴你是加密的問題。

不過的話，依序確認：
1. 順序是不是「JSON → URLEncode → AES → Base64」（**不是** AES → URLEncode）
2. URLEncode 是不是用 .NET 慣例（見 `references/urlencode-table.md`，
   空白編成 `+`、`!*()` 等符號的處理與一般 `encodeURIComponent` 不同）
3. 是不是 AES-**128**-CBC + **PKCS7**（不是 PKCS5、不是 zero padding）
4. HashKey / HashIV 是不是各**恰好 16 bytes**

## 檢查 2：`.env` 設定

**只檢查「有沒有設」與「格式對不對」，絕對不要把值印出來。**

```
.env 檢查

  OPAY_MERCHANT_ID    ✅ 已設定（2000132，測試環境 B2C 特店）
  OPAY_HASH_KEY       ✅ 已設定（長度 16 ✅）
  OPAY_HASH_IV        ✅ 已設定（長度 16 ✅）
  OPAY_HOST           ✅ https://einvoice-stage.opay.tw（測試環境）
  .env 是否被 git 追蹤 ✅ 否
```

常見錯誤：
- **長度不是 16**：多半是複製時多了空白或換行。
- **特店與金鑰不同組**：測試 B2C 特店 `2000132` 要配 B2C 的測試金鑰；
  離線測試特店是 `2045501`，金鑰也不同。混用會直接 `TransCode` 失敗。
- **host 與特店不同環境**：測試特店打正式 host，一定失敗。

## 檢查 3：系統時差

歐付寶的 `RqHeader.Timestamp` 驗證區間約 **10 分鐘**。
機器時鐘不準是「時好時壞」型故障的頭號原因，尤其是門市 POS 與長期沒重開的 VM。

```bash
# 看本機時間與 NTP 來源的差距
timedatectl status 2>/dev/null || date -u
```

```
時差檢查

  本機 UTC 時間：   2026-08-18T06:32:11Z
  NTP 同步：        ✅ 已同步
  估計時差：        +0.8 秒（容許約 ±600 秒）✅
```

沒開 NTP 的話，這就是要修的第一件事。

## 檢查 4：連線與唯讀 API 實測

**只用唯讀 API。正式環境也一樣，絕不可以用 `Issue` 或 `OfflineIssue` 做健檢** ——
那會產生真實發票，是稅務資料污染（見 `guides/24-prod-monitoring.md`）。

依序打這四支（都是唯讀）：

1. `GetInvoiceWordSetting` —— 只要年度就查得到，最適合當健康檢查
2. `CheckBarcode` —— 驗證一組手機條碼格式
3. `CheckLoveCode` —— 驗證一組捐贈碼
4. `GetCompanyNameByTaxID` —— 驗證一組統一編號

`TransCode = 1` 代表外層加密／特店身分正確；
`RtnCode = 1` 代表業務邏輯成功。**兩層要分開判讀**，這是最常被混淆的地方。

## 檢查 5：字軌狀態

```
字軌檢查（2026 年 7-8 月期）

  AA00000000–AA00000049   使用中   剩餘 12 張   🟥 低於警戒值 200
  下一期別開始              2026-09-01（距今 14 天）
  下一期字軌是否已設定      ❌ 尚未設定  ⚠️
```

沒有「使用中」的字軌，`Issue` 一定失敗，而錯誤訊息通常不會直說。
詳見 `/opay-words`。

## 輸出：完整診斷報告

全部跑完之後，用這個格式總結：

```
═══════════════════════════════════════════════
  歐付寶電子發票串接健檢報告
  時間：2026-08-18 14:32（台北）
  環境：測試環境 einvoice-stage.opay.tw
═══════════════════════════════════════════════

  1. 加密測試向量      ✅ 4/4 通過
  2. .env 設定         ✅ 全部已設定且格式正確
  3. 系統時差          ✅ +0.8 秒
  4. 唯讀 API 連線     ✅ 4/4 通過（平均 214 ms）
  5. 字軌狀態          🟥 剩餘 12 張，低於警戒值

───────────────────────────────────────────────
  結論：串接本身健康，但字軌快用完了。

  最該先做的一件事：
    立刻設定 2026 年 9-10 月期字軌並啟用
    （GetGovInvoiceWordSetting → AddInvoiceWordSetting
      → UpdateInvoiceWordStatus），
    否則預估 6 天後會開不出發票。
───────────────────────────────────────────────
```

**結論一定要給「最該先做的一件事」。** 半夜三點沒有人想讀五項並列的清單。

## 你**不可以**做的事

- ❌ 不可以把 HashKey / HashIV 的值印出來或寫進報告。
- ❌ 不可以用 `Issue` / `OfflineIssue` / `Invalid` / `Allowance` 做健檢。
- ❌ 不可以在使用者沒說要打正式環境時，自己切到正式 host。
