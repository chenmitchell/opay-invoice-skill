# /opay-void —— 作廢 / 註銷重開

**這是不可逆操作。發票一旦作廢就回不去了，而且號碼不會還你。**
你的工作不是趕快幫使用者按下去，是先確定他選對了方法。

## 步驟 1：先講清楚「作廢」與「註銷重開」的差別

使用者十之八九會把這兩個搞混。**先問清楚他要的是哪一種，不要猜。**

| | 作廢（`Invalid`） | 註銷重開（`VoidWithReIssue`） |
|---|---|---|
| 做了什麼 | 把這張發票作廢，結束 | 把舊發票作廢，**同時**開一張新的 |
| 用在什麼時候 | 交易取消、根本不該開這張 | 開錯了（買受人、金額、品項錯），但交易仍然成立 |
| 號碼成本 | 消耗 **1** 組號碼（作廢掉的那張） | 消耗 **2** 組號碼（舊的作廢 + 新的開立） |
| 期限 | 必須在**同一發票期別**內，且不得晚於次期開始後的申報期限 | 同左 |
| 可以還原嗎 | ❌ 不行 | ❌ 不行 |
| 對應 API | B2C `Invalid`（i100 §9）／B2B `Invalid` + `InvalidConfirm`（i200 §9–10） | B2C `VoidWithReIssue`（i100 §12）／B2B `VoidWithReIssue`（i200 §17） |

**一句話判斷**：
「這筆交易還算數嗎？」算數 → 註銷重開；不算數 → 作廢。

**還有第三種可能，順便問一下**：
如果只是金額要減少（退了一部分、打折後補差額），那**不是**作廢，
是**折讓**（`/opay-allowance`）。折讓不消耗發票號碼，成本低得多。

## 步驟 2：B2B 要提醒是兩段式

B2B 的作廢是 `Invalid` → 對方 `InvalidConfirm`。
**只送 `Invalid` 那張發票會一直停在「待確認」，不算作廢完成。**
退回（`Reject` → `RejectConfirm`）是另一條路徑：那是**買方**發起的。

## 步驟 3：查現況（不要憑使用者口述）

先用 `GetIssue` 把這張發票撈出來，唸給使用者聽：

```
即將作廢 / 註銷重開：
  發票號碼：  AA12345678
  開立日期：  2026-08-18
  期別：      2026 年 7-8 月期（是否仍在可作廢期間：✅ / ❌）
  買受人：    …
  總金額：    NT$ …
  目前狀態：  已開立 / 已作廢 / 已折讓（已折讓過的發票作廢前要先處理折讓）
```

**如果已經超過期別、或已經作廢過，直接停下來告訴使用者不能做，並說明替代方案。**

## 步驟 4：二次確認（不可省略）

用這個格式問，**並且要求使用者用文字回覆，不接受「好」「嗯」「yes」**：

```
確認一下：

  操作：      作廢（Invalid）
  發票號碼：  AA12345678
  金額：      NT$ 1,050
  環境：      正式環境 ⚠️
  號碼成本：  消耗 1 組號碼，不會歸還
  可逆性：    不可逆

這會產生真實的稅務紀錄。確定要執行請完整回覆：
「確認作廢 AA12345678」
```

註銷重開的版本要額外唸出**新發票的完整內容**與「消耗 2 組號碼」。

**使用者回覆的內容必須包含發票號碼**才算數。這是刻意的：
要他把號碼再打一次，就是逼他再看一眼。

## 步驟 5：執行與記錄

- `RtnCode = 1` 才算成功。
- 記錄：誰、什麼時候、作廢了哪張、原因是什麼。
  範本（`templates/telegram-bot/`、`templates/discord-bot/`）預設會寫 `audit.log`，
  這不是裝飾，是被查帳時唯一能證明「不是有人亂按」的東西。
- **失敗不要重試。** 先用 `GetInvalid` 查是不是其實已經成功了。

## 你**不可以**做的事

- ❌ 不可以在使用者沒有明確逐字確認前執行。
- ❌ 不可以「順便」把作廢與重開一起做完卻只確認一次。
- ❌ 不可以在使用者說「幫我全部作廢」時批次執行。逐張確認，或請他改用後台。
