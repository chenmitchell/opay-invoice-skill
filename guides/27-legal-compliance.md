# 27 · 台灣電子發票法遵重點

> ⚖️ **免責聲明：本文僅為參考，不構成法律或稅務意見。上線前請諮詢會計師或稅務顧問。**
>
> 本文整理的是**技術串接時會直接影響到的法遵面向**，供工程團隊在設計系統時知道「哪些地方不能只憑技術便利決定」。本文**不宣稱任何系統「已符合法規」**，也不取代專業意見。法規會修訂，實務見解會變動，請以主管機關最新公告與您的會計師意見為準。

> **對應 API**：無（本文為法遵說明）。技術細節見 [`references/`](../references/)。
> **前置條件**：已完成 [`02-preflight-checklist.md`](02-preflight-checklist.md)；已與會計師確認貴公司的申報方式與發票種類。

---

## 1. 為什麼工程師需要讀這一章

電子發票的許多「技術決定」其實是**法遵決定**：

| 看起來像技術問題 | 實際上是 |
|---|---|
| 「開立失敗要不要自動重試？」 | 重複開立會產生**重複的稅務憑證** |
| 「健康檢查打哪支 API？」 | 打 `Issue` 會產生**真實憑證** |
| 「發票 log 要留多久？」 | 涉及**營業人保存義務** |
| 「要不要存買受人 Email？」 | 涉及**個資最小蒐集原則** |
| 「載具欄位要不要預設勾選捐贈？」 | 涉及**消費者告知義務** |

> 🔑 **工程師不需要成為稅務專家，但需要知道「哪些決定要問會計師」。** 這一章的目的就是標示出那些點。

## 2. 上傳期限

| 體系 | 期限 | 出處 |
|---|---|---|
| **B2C** | 加值中心於 **48 小時內**協助上傳財政部 | i100 §7 |
| **B2B** | **7 天內**上傳財政部 | i200 |
| **離線** | 上傳發票的開立時間**不可超過下一期的 15 號** | i301 §13 |

### 2.1 工程上的意義

| 意義 | 說明 |
|---|---|
| **開立不能無限期延後** | 系統故障時的降級策略必須考慮期限，不能「等修好再開」 |
| **B2B 的 7 天包含對方確認的時間** | 交換模式下「等待確認」的發票也在倒數，見 [`14`](14-b2b-issue.md) §5 |
| **離線上傳佇列不能積壓過期** | 過期就上傳不了，該張發票在財政部端等於沒有開立紀錄，見 [`18`](18-offline-invoice.md) |
| 延遲開立要有逾時告警 | `DelayFlag=2` 沒被觸發**永遠不會開立**，見 [`04`](04-b2c-issue.md) §7 |

> ⚠️ **這裡列的是「加值中心的上傳期限」，不等於「營業人的開立期限」。** 發票應該在什麼時點開立（見 §3），是另一件事，且依交易類型而異。**請與會計師確認貴公司的正確開立時點。**

## 3. 發票開立時點

發票的開立時點依交易性質而異（例如買賣、承攬、租賃、預收貨款等各有規定），**這是稅務問題，不是技術問題**。

### 3.1 工程上要提供的彈性

正因為開立時點由業務性質決定，系統**必須支援多種開立時機**，而不是寫死「付款成功就開」：

| 業務情境 | 需要的能力 | 對應 API |
|---|---|---|
| 即時交付 | 立即開立 | `Issue` |
| 固定天數後交付 | 排程開立 | `DelayIssue` `DelayFlag=1` |
| 交付時點不定（預購、客製） | 事件觸發開立 | `DelayIssue` `DelayFlag=2` + `TriggerIssue` |
| 交付前取消 | 取消未開立的發票 | `CancelDelayIssue` |

> **為什麼這是法遵議題而不只是功能需求**：如果系統只支援「付款即開立」，那麼所有「應該在交付時才開立」的交易都會**開立時點錯誤**。這不是能靠事後作廢解決的問題——作廢有時間窗，而且大量作廢本身就會被關注。
>
> 🔑 **請在需求階段就問會計師：「我們這種交易，發票應該在什麼時候開？」** 這個答案決定了系統架構。

## 4. 載具、捐贈與消費者告知義務

### 4.1 三選一是消費者的權利

消費者有權選擇：**存入載具**、**捐贈**、或**索取紙本／打統編**。

| UI 設計 | 評價 | 為什麼 |
|---|---|---|
| 三個選項並列，預設「不選」或「存入載具」 | ✅ | 讓消費者主動選擇 |
| **預設勾選「捐贈」** | ❌ | 消費者可能在不知情的狀況下把發票捐出去，喪失中獎權利 |
| 只提供載具，沒有紙本選項 | ⚠️ | 應確認是否符合貴公司的營業型態，請諮詢會計師 |
| 把「索取紙本」藏在三層選單下 | ⚠️ | 形式上有、實質上沒有 |

> **為什麼「預設捐贈」特別有問題**：捐贈的發票**不能對獎**。消費者如果沒注意到預設值，等於在不知情下放棄了中獎機會。而且開立後要改回來，只能走註銷重開或折讓流程。

### 4.2 必須明確告知的事項

| 事項 | 為什麼要告知 |
|---|---|
| 選擇捐贈後**無法對獎、無法索取紙本** | 這是不可逆的選擇 |
| 有統一編號的發票**不能捐贈、不參與對獎** | 官方規則：有 `CustomerIdentifier` 時 `Donation` 必須 `0`；`IIS_Award_Flag` 會是 `X` |
| 存入載具後，中獎會自動通知 | 消費者不需要保留紙本 |
| **超商 KIOSK 只能列印一次** | 列印消費發票後，中獎也無法再印中獎發票，見 [`08`](08-b2c-notify-print.md) §4 |

> **告知的形式**：不是塞一段小字免責聲明。**在選項旁邊直接寫清楚後果**，例如「捐贈（不參與對獎，無法索取紙本）」。無障礙做法見 [`29-wcag-ui-ux.md`](29-wcag-ui-ux.md)。

## 5. 營業人保存義務

營業人有保存憑證與相關資料的義務（保存年限與範圍請依主管機關規定並與會計師確認）。

### 5.1 工程上要保存什麼

| 資料 | 為什麼 |
|---|---|
| 發票號碼、開立日期、金額、買受人資訊 | 憑證本體 |
| **`RtnCode` / `RtnMsg` 原文** | 官方沒有公開完整錯誤碼表，日後查證需要原始值 |
| `RelateNumber` 與訂單的對應 | 追溯「這張發票對應哪筆交易」 |
| **作廢／註銷／折讓的原因與操作者** | 稽核時要能解釋「為什麼這張發票沒了」 |
| 上傳狀態與時間 | 證明已在期限內上傳 |
| **空白未使用發票的申報紀錄** | 證明配出去的號碼都有交代，見 [`11`](11-b2c-blank-invoice.md) |
| Audit log | 誰在什麼時候做了什麼不可逆動作 |

> 🚫 **不要為了節省儲存空間而輪替刪除發票相關 log。** 一般應用的 log 保留 30 天很正常，但發票相關的操作紀錄不適用同一套策略。**保存年限請與會計師確認後再設定輪替規則。**

### 5.2 備份

| 對象 | 為什麼 |
|---|---|
| `invoice_state` 狀態表 | 冪等與對帳的基礎，見 [`22`](22-idempotency-and-retry.md) |
| Audit log | 不可逆動作的唯一紀錄 |
| **離線發票的本機號碼台帳** | 「已配發但未上傳」的狀態**只存在你的機台裡**，歐付寶不知道，見 [`18`](18-offline-invoice.md) §6 |
| bot 的 audit log 與狀態庫 | 危險操作的紀錄，見 [`25`](25-telegram-bot.md) |

## 6. 個人資料最小蒐集原則

發票流程會接觸到買受人的**Email、手機號碼、統一編號、公司名稱與地址**。

### 6.1 只蒐集必要的

| 欄位 | 什麼時候真的必要 |
|---|---|
| `CustomerEmail` | 要寄發票通知時（且 `CustomerPhone` 為空時為必填） |
| `CustomerPhone` | 要發簡訊通知時（且 `CustomerEmail` 為空時為必填） |
| `CustomerName` / `CustomerAddr` | **`Print=1`（要列印）時為必填**；不列印時不需要 |
| `CustomerIdentifier` | 消費者要求開立統編發票時 |

> **官方規則本身就體現了最小蒐集**：`CustomerEmail` 與 `CustomerPhone` 是**二擇一**必填，不是兩個都要。`CustomerName` / `CustomerAddr` 只在列印時必填。**不要為了「資料完整」而全部強制填寫。**

### 6.2 測試環境

> ⚠️ **官方明訂：測試環境請勿帶入真實電子信箱，避免個資外洩。** 而且測試環境「僅以 API 回覆成功或失敗，**不提供發信測試，僅驗規則**」。

**測試資料建議**：用 `test+{orderId}@example.invalid` 這類明確不可送達的位址。

### 6.3 存取控制

| 場景 | 風險 | 對策 |
|---|---|---|
| bot 綁到全公司大群組 | 全公司看得到買受人 Email／手機／統編 | 綁專用私有頻道，定期檢視成員，見 [`25`](25-telegram-bot.md) §8 / [`26`](26-discord-bot.md) §6 |
| 客服後台顯示完整資料 | 過度暴露 | 依角色遮蔽（例如只顯示 Email 前 3 碼） |
| Log 印出完整 payload | 個資落進 log 系統 | 對 Email／手機做遮蔽後再寫 log |
| 錯誤回應直接吐 `RtnMsg` 給前端 | 可能含內部資訊 | 給參考碼，見 [`19`](19-backend-fastapi.md) §6 |

### 6.4 保存與刪除的張力

⚠️ **這裡有一個需要專業判斷的衝突**：稅務上有**保存義務**，個資上有**最小蒐集與適時刪除**的要求。兩者如何平衡，**請諮詢會計師與法務**，不要由工程團隊自行決定保留策略。

## 7. 不可逆動作的內控

作廢、註銷重開、折讓都會產生稅務紀錄。這些動作的**內部控制**是法遵的一部分。

| 控制 | 做法 |
|---|---|
| 權限 | 只有特定角色能執行 |
| **二次確認** | 一次性驗證碼，見 [`25`](25-telegram-bot.md) §7 |
| **原因記錄** | 用固定分類 + 關聯單號，不要自由輸入，見 [`06`](06-b2c-invalid-void.md) §9 |
| Audit log | 操作者、時間、對象、原因、結果 |
| 定期檢視 | 作廢率、作廢原因分佈，見 [`06`](06-b2c-invalid-void.md) §10 |
| **B2B 存證模式的「合意」** | 官方要求作廢／退回前須與交易相對人達成合意；程式驗證不了，要靠流程與勾選紀錄 |

> 🚫 **「重複開立」造成的作廢應該是 0。** 大於 0 代表冪等機制有破口。這不只是技術問題——每一張重複的發票都曾經是一筆**錯誤的稅務憑證**。

## 8. 上線前要問會計師的問題清單

工程團隊自己回答不了，但必須有答案的問題：

```
開立
[ ] 我們這種交易，發票應該在什麼時點開立？
[ ] 我們適用哪種字軌類別（07 一般稅額 / 08 特種稅額）？
[ ] 我們有沒有零稅率、免稅或特種稅額的交易？對應的欄位怎麼填？
[ ] 我們需不需要申請 TaxType=9（混合稅率）？

B2B
[ ] 我們要用存證還是交換模式？不同客戶可以不同嗎？
[ ] 我們需不需要接收進項發票？

流程
[ ] 退貨退款要走折讓還是作廢？各自的內部核准流程是什麼？
[ ] 期末空白未使用發票由誰負責申報？
[ ] 誰有權限執行作廢與折讓？

保存
[ ] 發票相關資料要保存多久？
[ ] 個資（買受人 Email／手機）的保留期限如何與保存義務平衡？

其他
[ ] 我們的載具／捐贈 UI 呈現方式是否妥適？
[ ] 我們需不需要提供紙本發票的選項？
```

> **為什麼要列成清單**：這些問題在開發後期才問，往往會導致架構性的返工。**在需求階段一次問完**，比事後補救便宜非常多。

### 常見錯誤

1. **把「加值中心 48 小時上傳期限」當成「開立期限」。** 兩者是不同的事。開立時點由交易性質決定，請諮詢會計師。
2. **系統只支援「付款即開立」。** 許多交易應該在交付時才開立。架構要支援延遲與觸發開立。
3. **載具選項預設勾選捐贈。** 消費者可能在不知情下放棄中獎權利，且不可逆。
4. **發票 log 套用一般 30 天輪替。** 涉及保存義務，保留策略要與會計師確認。
5. **在測試環境用真實 Email。** 官方明訂禁止，且測試環境本來就不發信。
6. **把 bot 綁到全公司群組。** 發票明細含買受人個資。
7. **由工程團隊自行決定個資保留期限。** 稅務保存義務與個資刪除要求會衝突，需要專業判斷。
8. **宣稱系統「已符合法規」。** 沒有任何技術文件（包含本文）能做這個保證。
