## 0. 🚫 官方沒有公開完整錯誤碼表

三份官方文件的附錄都只有一句話：

> 因錯誤代碼一直在新增，詳細的錯誤代碼，請到**廠商後台 → 電子發票後台 → 系統開發管理 → 錯誤代碼查詢**。

| 環境 | 後台 |
|---|---|
| 測試 | `https://vendor-stage.opay.tw` |
| 正式 | `https://vendor.opay.tw` |

**官方文件中明確寫出意義的 `RtnCode` 只有這四個**：

| `RtnCode` | 意義 | 出處 |
|---|---|---|
| `1` | 成功（絕大多數 API） | 全篇 |
| `4000003` | **延後開立成功**（`DelayDay > 0`） | i100 §7 |
| `4000004` | **開立發票成功**（`DelayDay = 0`） | i100 §7 |
| `10000010` | 財政部系統維護中，無法驗證，請稍後再試 | i100 §20 §21 |

> 🚫 **不要在程式裡建一張自己編的錯誤碼對照表。** 如果你看到一份宣稱有完整清單的「歐付寶錯誤碼對照表」，它不是來自這三份官方文件。硬編猜測的表會造成「你的程式說是 A 錯誤，實際是 B 錯誤」的災難性誤導。
>
> **正確做法**：`RtnCode` / `RtnMsg` **原樣**寫進 log 與資料庫；對外用通用文案 + 參考碼；要查意義就登入後台。

## 1. 快速分診：先確認你在哪一層

```
HTTP 沒回應 / 逾時            → §2 連線層
HTTP 200 但 TransCode != 1    → §3 外層（時間 / 金鑰 / MerchantID）
TransCode=1 但解密失敗        → §4 加解密
解密成功但 RtnCode 非成功碼    → §5 業務層
全部成功但行為不如預期        → §6 語意誤解
```

> **為什麼先分層**：電子發票的失敗訊息普遍籠統。**先確定層級，比逐一試參數快十倍。**

## 3. 外層：`TransCode != 1`

`TransCode` 的官方定義是「傳輸資料（`MerchantID`、`RqHeader`、`Data`）**接收成功**」。非 `1` 代表這三者之一有問題。

| 症狀 | 可能原因 | 檢查什麼 | 出處 |
|---|---|---|---|
| **間歇性失敗，重跑有時就好** | 🚨 **主機時差** | 「合作特店須進行主機『**時間校正**』」。`timedatectl` / `chronyc tracking` | 各章 `RqHeader.Timestamp` |
| 提示時間相關錯誤 | `Timestamp` 超出驗證區間 | 「驗證時間區間**暫訂為 10 分鐘內有效**」 | 同上 |
| **全部請求都失敗** | `Timestamp` 用了**毫秒** | 是 Unix **秒**。JS 的 `Date.now()` 要 `/1000` 取整 | 同上 |
| **排程／批次失敗、即時作業正常** | 先組好 payload 排隊很久才送 | `Timestamp` 要在**實際送出前**才產生 | 同上 |
| 重試幾次後全失敗 | 重試沿用第一次的 `Timestamp` | 每次重試都要**重新產生** | 同上 |
| 一直失敗且與時間無關 | `MerchantID` 與金鑰**不是同一組** | 測試 B2C 是 `2000132`＋對應金鑰；離線是 `2045501`＋另一組金鑰 | 各 reference 共通事項 |
| 平台商相關失敗 | `PlatformID` 填了值 | **一般廠商必須留空字串** | 各章 `PlatformID` |

## 4. 加解密

| 症狀 | 可能原因 | 檢查什麼 | 出處 |
|---|---|---|---|
| `Data` 解析失敗，但本地 JSON 合法 | 忘記 URLEncode 或順序顛倒 | 順序必須是 **JSON → URLEncode → AES → Base64**；解密反向 | i100 附錄 3 |
| **只有含 `!` `*` `(` `)` 或空格的資料才失敗** | 沒做 .NET URLEncode 校正 | 見 §4.1 | i100 附錄 2 |
| 金鑰長度錯誤 | 用了 AES-256 或對 HashKey 做了 hash | 固定 **AES-128-CBC / PKCS7**，HashKey / HashIV 各 **16 個 ASCII 字元原樣使用** | i100 附錄 3 |
| 解密後尾巴多出 `\0` | 用了 zero padding | 必須是 **PKCS7** | 同上 |
| 傳輸被截斷 | Base64 帶了換行 | Base64 必須單行 | — |
| AES 解密失敗 | HashKey / HashIV 錯，或**測試與正式混用** | 逐字比對 16 碼，確認沒有多餘空白／換行 | — |

### 4.1 URLEncode 的語言差異（最常見的隱性 bug）

| 字元 | .NET（歐付寶要的） | PHP `urlencode` | PHP `rawurlencode` | JS `encodeURIComponent` | Python `quote_plus` |
|---|---|---|---|---|---|
| 空格 | `+` | `+` ✅ | `%20` ❌ | `%20` ❌ | `+` ✅ |
| `*` | 不編碼 | **`%2A`** ❌ | `%2A` ❌ | `*` ✅ | `%2A` ❌ |
| `!` | 不編碼 | `%21` ❌ | `%21` ❌ | `!` ✅ | `%21` ❌ |
| `(` `)` | 不編碼 | `%28` `%29` ❌ | `%28` `%29` ❌ | `(` `)` ✅ | `%28` `%29` ❌ |
| `~` | `%7E` | `%7E` ✅ | `~` ❌ | `~` ❌ | `~` ❌（3.7+） |

> 🚨 **PHP 的 `%2A` 陷阱**：`urlencode()` 會把 `*` 編成 `%2A`，但歐付寶要求**不編碼**。官方文件本身就提供了 `str_replace` 校正範例，代表這是**已知且要你自行處理**的差異。
>
> **為什麼這個 bug 會活很久**：`!*()` 在一般商品名稱裡不常出現。測試環境用「測試商品」永遠不會踩到；某天有個商品叫「限量！特價(買一送一)」就爆炸，而錯誤訊息只是籠統的參數錯誤。
>
> **驗證方法**：跑 [`test-vectors/`](../test-vectors/) 的驗證器，或 [`23-test-console.md`](23-test-console.md) 的六步自我驗證第②步。**測試資料一定要包含空格與 `!*()~`。**

完整轉換表與三語言修正實作見 [`urlencode-table.md`](../references/urlencode-table.md)。

> **為什麼要放進排錯文件**：撞到時間窗的失敗，`RtnMsg` 可能只寫一句籠統訊息，開發者會誤以為參數錯而不斷重試。**先確認是不是撞到時間窗，比翻參數快得多。**

## 6. 語意誤解：「成功了但行為不對」

| 症狀 | 真正原因 | 出處 |
|---|---|---|
| **開立成功卻被判成失敗，然後重複開立** | 用 `if RtnCode == 1` 判斷。開立的成功碼是 **`4000004`**（或延後開立的 `4000003`） | i100 §7 |
| 條碼明明不存在卻放行了 | `RtnCode=1` 只代表**呼叫成功**，還要看 **`IsExist`** | i100 §20 §21 |
| 線上折讓「成功」但實際沒開立 | `RtnCode=1` 僅代表 API 呼叫成功，**需消費者同意**後才算開立成功 | i100 §9 |
| 查不到已申請的線上折讓 | `GetAllowanceList`「**不包含消費者尚未同意之線上折讓單**」 | i100 §14 |
| B2B 發票狀態卡在「處理中」永遠不動 | `Upload_Status=2` 是**上傳失敗**（終態），不是處理中。B2C 只有 `0`/`1` | [`enums.md` §10.6](../references/enums.md#106-️-上傳狀態家族--b2c-兩值b2b-三值) |
| `ExchangeStatus` 判斷不一致 | 存證模式 `1`=完成（沒有 `0`）；交換模式 `0`=等待確認、`1`=已確認。**空值 = 未設定 ≠ `0`** | i200 §18 |
| 統編查回來是 `0000000000` | 代表**沒有統編**，不是統編是零 | i100 §13 |
| 稅金查回來是 `0` | 沒有統編時「稅金包含在發票金額內，**不拆算稅金**」 | i100 §13 |
| `IIS_Carrier_Num` 拿不到隱碼 | `CarrierType=4~8` 時「因有資安考量，**不會回傳隱碼 id**」，回的是顯碼 | i100 §13 |
| 中獎統計怪怪的 | `IIS_Award_Flag` **空值 ≠ `0`**：空值 = 不可對獎（如捐贈）、`0` = 對過獎沒中、`X` = 有統編之發票 | i100 §13 |
| 獎金排序錯誤 | `IIS_Award_Type` **數值大小 ≠ 獎金大小**（`8` 特別獎一千萬 > `7` 特獎二百萬 > `1` 頭獎二十萬） | i100 §13 |
| 通知重複寄兩封 | 後台通知開關與 `InvoiceNotify` **兩邊都開** | i100 §18 |
| 測試環境沒收到通知信 | 「測試環境下歐付寶**不會主動發送任何通知**」，需於後台「補發通知」 | i100 §18；i200 §4 |
| 測試環境收不到 `NotifyURL` | 「使用測試環境時，**不提供 NotifyURL 開立通知**」 | i100 §7 |
| `QRCode_Left`/`Right` 是空的 | 須先**申請密碼種子**才會協助壓碼回傳 | i100 §13 §19 |
| QR Code 內容不完整 | 「為避免過於複雜無法辨識，**QR Code 僅顯示前 2 個品項**」 | i100 §13 |
| KIOSK 中獎發票印不出來 | 已列印過消費發票；**只能列印一次**，之後中獎也無法再印 | i100 §7 |
| 設定 API 把別的設定清掉了 | 設定類是**覆寫語意**，不是 patch。要先 Get 再整組送 | i100 §24 §25 |
| `CostomerSetting` 一直失敗 | 官方欄位名就是拼作 **`Costomer`**，不是 `Customer` | i100 §23 §24 |
| `SelfSetting` 的 `NotifySwitch` 送 `3` 被拒 | `CostomerSetting` 是 `0`–`5`；**`SelfSetting` 只有 `0`/`1`** | [`enums.md` §10.5](../references/enums.md#105-️-notifyswitch--notifytype--同一個-request-body-裡兩套) |

| 捐贈碼捐錯機構 | 捐贈碼**首位可以為零**，用整數存 `0123` 會變 `123` | i100 §21 |

## 7. 官方文件本身的已知瑕疵

介接時會遇到、但**不是你的錯**的情況（原文照錄，介接前建議向歐付寶確認）：

| 位置 | 瑕疵 |
|---|---|
| `QueryBlankInvoiceList` | `InvType` 參數表寫 `"07"`／`"08"`，**回傳範例出現數值 `7`**；範例未含 `TotalCount`；傳入範例用了 Word 智慧引號 `“ ”` |
| `BlankInvAutoUploadSetting` | `IsAutoUpload` 型態標 String，**範例送數值 `1`**；`SettingList` 說明欄疑為誤植 |
| `DownLoadBlankInvList` | 名為「下載」，但**回傳只有 `RtnCode`/`RtnMsg`，未定義任何檔案內容或連結** |
| `GetInvoiceNotifySetting` / `GetRemainNotifySetting` | 回傳範例標示「(待調整)」，欄位與參數表不完全一致 |
| B2C `VoidWithReIssue` | 回傳範例的 `InvoiceNo` 值與 `RelateNumber` 相同，與 String(10) 定義不符 |
| `GetInvalid`（B2C） | 回傳外層範例出現參數表未列的 `EncData` |
| `GetInvoiceWordSetting` | `InvoiceInfo` 標為 Array 但範例寫成物件；**程式要能同時吃 list 與 dict** |
| 離線取號 API | 自動配號的切分規則未說明；「依數量」取號**沒有指定筆數的參數** |
| B2B 折讓類查詢 | 傳入無 `InvoiceCategory`，但回傳說明卻依它決定欄位是否為空 |
| `GetAllowanceInvalid`（B2B） | 統編欄位名是 `BuyerId`/`SellerId`，與其他 API 的 `Buyer_Identifier`/`Seller_Identifier` 不同 |

> **工程上的因應**：對這些欄位一律**寬鬆解析**（同時接受 `"07"` 與 `7`、同時接受 list 與 dict、缺欄位時用預設值），並在程式碼裡加註解說明原因，避免下一個人「修正」掉這些容錯。

### 常見錯誤

1. **在網路上找「歐付寶錯誤碼對照表」照抄。** 官方沒有公開完整清單。硬編猜測的表會造成比沒有更嚴重的誤導。
2. **看到失敗就先改參數。** 先分層（連線／外層／加解密／業務／語意），比逐一試參數快十倍。
3. **忽略「間歇性失敗」。** 那幾乎一定是主機時差。`Timestamp` 只有 10 分鐘驗證區間。
4. **測試資料不含空格與 `!*()~`。** URLEncode 的 bug 只有在資料含這些字元時才會出現。
5. **把撞到時間窗當成參數錯誤而重試。** 奇數月 13 號後不能作廢前兩個月的發票，重試一百次也一樣。
6. **把「原文瑕疵」當成自己寫錯而反覆修改。** 官方文件確實有不一致之處，要寬鬆解析並加註解。
7. **`RtnCode=1` 就當成功。** 開立要看 `4000004`；驗證要看 `IsExist`；線上折讓要等消費者同意。
