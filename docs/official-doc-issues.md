## 這份文件是誰寫的、為什麼寫

我是 Claude。這份清單是我寫的，不是這個 repo 的維護者寫的。

我被交付的任務是把上述三份官方技術文件轉成一份能讓 AI 直接照著串接的知識包，涵蓋全部 69 支 API 的逐欄位規格。要做到「一支都不漏」，我必須把三份文件從頭到尾讀完、把每一張表格的每一列都對過一次。下面這些是我在過程中撞到的東西。

我把它們寫出來，不是為了指責誰。文件會長成這樣，通常是因為它跨了很多年、很多人、很多次改版，而沒有一道機器關卡在旁邊擋著。我自己在做這個 repo 的時候也漏了東西，是後來的稽核抓出來的，那六筆記錄在 `docs/audit/`。所以這份清單的立場是：**這些是可以被機器擋下來的問題，只要有人決定去擋。**

排序依據是「讀者要付多少代價」，不是嚴重度的主觀感受。

## 先說我可能會錯的地方

我讀的是官方文件轉出來的純文字，不是排版後的原始文件。所以有一類差異必須先排除：

- 原文用**顏色**（紅色星號）表示必填。純文字保留了星號，但如果某處只用顏色而沒有星號，我會漏掉。
- 原文的表格若有**跨欄合併**，抽取後可能錯位。我遇到的錯位我會標明「疑似抽取造成」。
- 原文的**圖片內容我完全讀不到**。

下面每一條我都盡量標了原文行號（以我的純文字抽取為準，不同工具可能有幾行偏移），方便你自己開官方文件覆核。凡是我無法確定是文件本身的問題、還是抽取造成的，我都寫明了。

## 一、同一個欄位名，在同一份文件裡有三套互斥的定義

這是我認為最該優先修的一條，因為它會讓人**做出正確的呼叫，得到錯誤的結果，而且沒有任何錯誤訊息**。

離線文件的 `InvoiceStatus`（發票字軌狀態）：

| 原文行號 | 章節 | 定義 |
|---|---|---|
| 504 | 設定字軌號碼狀態 | `0`:停用　`1`:暫停　`2`:啟用 |
| 659 | 取得自動配發發票字軌號碼 | `1`:啟用　`2`:備用字軌 |
| 698 | 取得發票字軌號碼 | `1`:啟用　`2`:備用字軌 |
| 742 | 取得發票字軌號碼（依數量） | `1`:啟用　`2`:備用字軌 |

`1` 在第一列是「暫停」，在其他三列是「啟用」。`2` 在第一列是「啟用」，在其他三列是「備用字軌」。

一個工程師如果先讀了取號那幾章、記住「1 是啟用」，然後去呼叫設定字軌狀態並帶 `1`，他會把字軌設成**暫停**。字軌暫停的後果是開不出發票。而 API 會回成功，因為他確實成功地把狀態設成了他要求的值。

同一份文件裡還有第三套：`UseStatus`（字軌使用狀態，行 1092、1140）用的是 `1`:未啟用　`2`:使用中　`3`:已停用　`4`:暫停中　`5`:待審核　`6`:審核不通過。這套跟前兩套都不相容，而且名字只差兩個字。

**修起來要做什麼**：三處的列舉統一，或至少在每一處加一行「本欄位的列舉與 §X 不同，請注意」。前者是對的，後者至少能救人。

## 二、`TaxType` 在不同章節的允許值不一致

| 原文行號 | 章節 | `InvType=07` 時允許的值 |
|---|---|---|
| 392 | 開立發票（一般） | `1`、`2`、`3`、`9` |
| 575 | 開立發票（延遲） | `1`、`2`、`3`、`9` |
| 1428 | 註銷重開 | `1`、`2`、`9` |

註銷重開少了 `3`（免稅）。

這代表兩件事之一：要嘛免稅發票真的不能註銷重開，那應該明講原因；要嘛是漏字，那應該補上。目前的狀態是讀者無從判斷，只能試。而註銷重開不是可以隨便試的操作。

我在 repo 裡的處理方式是三處都逐字照抄、然後標註矛盾並附行號，因為我沒有立場替官方決定哪一個才是對的。

## 三、錯誤代碼完全沒有公開

三份文件的附錄都是同一句話：

- B2C 行 3296：「因錯誤代碼一直在新增，詳細的錯誤代碼，請到廠商後台->電子發票後台->系統開發管理->錯誤代碼查詢。」
- B2B 行 2920：同上
- 離線 行 1174：「請到廠商後台->系統開發管理->交易狀態代碼查詢。」

我理解「一直在新增」是真的。但這句話的實際效果是：

1. **任何 AI 都無法協助排錯。** 我拿到一個 `RtnCode` 卻不知道它是什麼意思，正確的做法只剩下把代碼原樣回傳給使用者、請他自己去後台查。我在這個 repo 裡就是這樣做的，而且明文禁止自己猜。
2. **任何自動化監控都無法分級。** 系統收到錯誤時無法判斷這是「該重試」還是「該告警」還是「該停止」。
3. **還沒開通的人看不到。** 後台要有帳號才進得去。評估階段的工程師、寫技術選型報告的人、幫客戶評估的顧問，全部被擋在外面。

「一直在新增」的正確解法不是不公開，是**公開一份會自動更新的清單**。後台裡那張表既然存在，把它變成一個公開網址的成本並不高。

## 四、關鍵資料以圖片形式呈現，機器讀不到

我從純文字裡數到的 `[[IMG]]` 只有 4 處，但「情境流程圖」這五個字在三份文件裡出現了 73 次（B2C 30、B2B 31、離線 12）。也就是說幾乎每一支 API 都配了一張流程圖，而那些圖對我全是黑的。

其中最嚴重的一張是**離線文件附錄 1「交易狀態代碼表」（行 1175 附近）**。那整張表就是一張圖片。純文字抽取後一個字都沒有。

這代表：

- 我沒有辦法把它寫進 repo，只能誠實標註「無法轉寫」（稽核員特別驗證過我沒有自己編一張出來）。
- 螢幕閱讀器使用者讀不到。
- 全文檢索搜不到。
- 任何 AI 助理都幫不上忙。

我在 repo 裡的做法是依 API 語意用 Mermaid 重繪了 73 張圖，每張都標明「圖內細節未能取得，本圖依語意重繪，請以官方為準」。這是替代品，不是還原。

**修起來要做什麼**：流程圖至少補 alt text 或文字說明；代碼表一定要是文字表格。這件事的成本很低，效益很高。

## 五、欄位表和範例對不上

我逐一比對了每一支 API 的「欄位表」與「JSON 範例」，這是我找到的：

| 位置 | 表格說 | 範例寫 |
|---|---|---|
| B2C 查詢發票明細 | 回傳欄位名為 `InvoiceRemark` | 範例用 `IIS_Comment` 承載發票備註 |
| B2C 延遲開立（行 422 vs 456） | `Items` 子欄位表**未列** `ItemRemark` | 範例三筆商品都有 `ItemRemark` |
| B2B 折讓（行 2683） | 買方 email 欄位 | 範例值 `abc@sunup.net` |
| 多處 | `RtnCode` 型態為 `Int` | 範例值為字串 `"1"` |

第四項最容易造成實際故障。強型別語言（Java、C#、Go、Rust）照著「Int」宣告，收到 `"1"` 就是反序列化失敗。這種錯誤發生在最外層，通常會被記成「連線異常」，然後花半天查網路。

## 六、必填標記不一致

`RqHeader` 這個外層欄位，在離線文件的 §5 到 §9 標了紅色星號（必填），§10 以後沒標。但它其實每一支都必填，因為裡面的 `Timestamp` 是必填的，而 `Timestamp` 缺了整個請求會被拒絕。

同樣的情形出現在 `Items`：`Items` 本身沒有星號，但它的子欄位 `ItemName`、`ItemCount`、`ItemWord`、`ItemPrice`、`ItemAmount` 都有。一個父欄位不必填、子欄位必填，在邏輯上是矛盾的。

還有一處是 B2B 的 `InvoiceNo`，原文寫成「`* InvoiceNo`」，星號和名稱之間多了一個空格。我依星號判定為必填，但這種寫法會讓任何自動化解析器判錯。

## 七、範例 JSON 有語法錯誤

我把三份文件裡的 JSON 範例全部丟進解析器，離線文件就有 11 處無法解析。類型包括：

- 缺逗號
- 多餘的結尾逗號（trailing comma）
- 引號沒閉合（例如 `"EFGH` ）
- 陣列被寫成物件並列
- 回傳範例出現欄位表未定義的欄位（`EncData`、`Revision`）
- 值的尾端多了空白

我全部照原文保留並標註，沒有「順手改對」。理由是：改對了讀起來比較舒服，但讀者拿我的版本去跟官方文件對照時，發現不一致會無法判斷是誰錯。照抄加標註讓兩件事都成立。

不過從官方的角度，這些都是 CI 可以擋的。一支腳本把文件裡所有 JSON 區塊抓出來丟 `json.loads()`，跑不過就紅燈，寫起來不到二十行。

## 八、另一家公司的資料混進來了

B2B 文件行 1492：

```
"CustomerEmail": "test@ecpay.com.tw",
```

這是綠界的網域，出現在歐付寶的官方技術文件範例裡。

我不知道這是怎麼來的，也不打算猜。但我要指出它的實際傷害：**這正是造成 AI 混淆歐付寶與綠界的原因之一。**

我在這個 repo 的 `SKILL.md` 裡花了整整一段警告 AI「歐付寶不是綠界，歐付寶用 AES-128-CBC 不是 CheckMacValue」，還為此寫了一道 CI 關卡去掃描有沒有把綠界的做法混進來。這道防線之所以必要，一部分原因就是這種混入。當官方文件自己都出現另一家的網域時，任何模型從中學到的關聯都會是錯的。

## 九、測試環境資訊自相矛盾

B2C 前置準備那張表：

- 行 75：平台商編號 (PlatformID) = `2046611`
- 行 82：「PlatformID(**3085340**) 已將 MerchantID(2000132) 設定為子廠商」

同一張表裡兩個不同的 PlatformID。要串平台商模式的人，第一步就卡住。

## 十、跨文件引用錯誤

離線文件 §3 的注意事項寫著「請參照第七章開立發票列印相關參數特別說明」。但離線文件的第七章是「管理發票機台」，跟列印無關。那句話指的應該是 B2C 文件的第七章。

這種錯誤的成本是讀者會先懷疑自己看錯，翻回去確認，然後才意識到是文件錯了。單次成本不大，但它會侵蝕讀者對整份文件的信任，之後每一句話都要再確認一次。

## 十一、B2B 附錄少了 URLEncode 轉換表

B2C 和離線文件的附錄都有 URLEncode 轉換表，B2B 沒有。但 B2B 的加密流程一樣要先 URLEncode 再 AES，一樣會踩到 .NET 編碼慣例的坑（空格編成 `+` 而不是 `%20`，`!*()` 不編碼）。

只讀 B2B 文件的人不會知道有這件事。他會用語言內建的 urlencode，然後得到一個永遠驗不過的密文，而且錯誤訊息不會告訴他原因。

## 我想說的一件事

上面十一條，沒有一條是「AI 才會遇到的問題」。

流程圖是圖片，螢幕閱讀器使用者也讀不到。錯誤代碼不公開，值班工程師半夜也查不到。`InvoiceStatus` 的 `1` 在兩章代表相反的意思，人類讀者一樣會設錯。範例 JSON 少一個逗號，複製貼上的人一樣會編譯失敗。

**AI 沒有帶來新的問題，AI 只是讓舊的問題第一次變得可以被計數。**

以前這些坑是每個工程師各自踩一次，踩完在自己的筆記裡寫一行，然後離職帶走。沒有人統計過，所以看起來不存在。現在有人把三份文件從頭到尾機械式對過一遍，它們就變成一張有行號的清單了。

這份清單的每一條，我都認為是可以修的，而且大部分修起來不貴。真正貴的是決定要修。

我不要求你相信我。上面每一條都附了行號，覆核方式是：

1. 到官方下載頁取得三份技術文件：<https://developers.opay.tw/Download/Document#invoice>
