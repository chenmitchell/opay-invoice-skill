# docs/prompt-examples.md — 自然語言指令範例

把本 Skill 載入 AI 助手後（步驟見 [`SETUP.md`](../SETUP.md)），直接用中文問就好。

以下是 **30 條實測有效的提問範例**，依情境分類。你可以直接複製，把角括號裡的內容換成你的實際需求。

---

## 怎麼問才問得好

| 原則 | 為什麼 | 範例 |
|---|---|---|
| **講明是歐付寶** | AI 容易把綠界 ECPay 的做法混進來 | 「**歐付寶（O'Pay）** 電子發票的…」 |
| **講明 API 名稱** | 規格檔很長，指名道姓檢索命中率最高 | 「`AllowanceByCollegiate` 的必填欄位有哪些」 |
| **講明 B2C / B2B / 離線** | 三套 API 欄位不同 | 「**B2B 交換模式**下的作廢流程」 |
| **講明語言與框架** | 直接產出可用的程式碼 | 「用 **Python FastAPI**…」 |
| **要求引用來源** | 可以自己回頭驗證 | 「請引用 `references/` 中的檔案與章節」 |
| **要求先查再答** | 降低幻覺 | 「請先讀 `references/enums.md` 再回答，不要憑記憶」 |

> ⚠️ **提問時不要貼真實金鑰、真實發票號碼、買受人個資。** 先脫敏，見 [`SECURITY.md`](../SECURITY.md)。

## 一、入門與環境（1–4）

**1. 完全沒串過，從哪開始**
```
我完全沒串過台灣的電子發票，公司要用歐付寶（O'Pay）。
請依 guides/00-onboarding.md 與 guides/02-preflight-checklist.md，
列出我在寫任何程式碼之前必須先完成的事，以及每一項的負責人通常是誰（工程／財會／老闆）。
```

**2. 環境檢查**
```
我要開始串歐付寶電子發票測試環境。
請幫我列一份 preflight 檢查清單：主機時間、TLS 版本、防火牆 FQDN、
金鑰與 MerchantID 配對、財政部平台授權狀態。
每一項請說明「沒做會出現什麼症狀」。
```

**3. 驗證我的加密實作**
```
請說明歐付寶電子發票的 Data 欄位加密流程，
並用 test-vectors/aes-encryption.json 的第一組官方向量，
一步一步示範：明文 JSON → URLEncode → AES-128-CBC → Base64，
每一步的中間結果都印出來。
```

**4. 我從綠界搬過來**
```
我們原本用綠界 ECPay 的電子發票，現在要換成歐付寶。
請列出兩者在「加密驗證方式、host、路徑前綴、外層欄位、回應碼結構」上的差異，
並明確指出我原本的哪些程式碼一定要重寫。
```

## 二、B2C 開立（5–10）

**5. 最小可用的開立**
```
用 Python + requests 寫一支最小可用的歐付寶 B2C 開立發票函式，
呼叫 /B2CInvoice/Issue，欄位請照 references/b2c-api-reference.md，
TransCode 與 RtnCode 兩層都要檢查，錯誤訊息要帶繁中修復建議。
金鑰從環境變數讀，不要寫死。
```

**6. 手機條碼載具**
```
買受人要用手機條碼載具開立 B2C 發票。
請說明 CarrierType 與 CarrierNum 該怎麼填，
以及為什麼開立前一定要先呼叫 CheckBarcode 驗證。
請一併給我驗證失敗時的處理建議（要不要擋下訂單）。
```

**7. 捐贈發票**
```
消費者選擇捐贈發票給社福團體。
請說明 Donation 與 LoveCode 的填法，
以及 CheckLoveCode 驗證失敗時該怎麼處理（愛心碼被停用的情況）。
```

**8. 開給公司（有統編）**
```
B2C 發票要開給有統一編號的公司行號。
請說明 CustomerIdentifier 的填法，
以及填了統編之後哪些欄位就不能填（載具、捐贈）。
另外請說明 GetCompanyNameByTaxID 該在流程中的哪個位置呼叫。
```

**9. 延遲開立**
```
我們是預購商品，出貨後才開發票。
請說明 DelayIssue、TriggerIssue、CancelDelayIssue 三者的關係與使用時機，
並畫一張狀態機圖（配色請遵循 docs/accessibility.md）。
```

**10. 品項與稅額**
```
一張發票裡有應稅商品和免稅商品混在一起。
請說明歐付寶 B2C Issue 的 TaxType 與品項欄位該怎麼處理，
含稅未稅的四捨五入要注意什麼，以及為什麼實務上建議拆單。
```

## 三、字軌與配號（11–13）

**11. 第一次設定字軌**
```
我拿到財政部的配號了，字軌 AB，號碼 12340000 到 12349999。
請一步一步教我用歐付寶 API 完成設定：
GetGovInvoiceWordSetting → AddInvoiceWordSetting → UpdateInvoiceWordStatus，
每一步的必填欄位與常見錯誤都要說明。
```

**12. 期別交界**
```
下個月就要跨期別了（11-12月 → 1-2月）。
請列出我在交界前必須完成的事，
以及「沒設定下一期字軌」會在哪一天、以什麼症狀爆炸。
請給我一份可以放進行事曆的檢查清單。
```

**13. 餘量監控**
```
請用 Python 寫一支排程腳本，
每小時呼叫 GetInvoiceWordSetting 檢查使用中字軌的剩餘張數，
低於門檻就推播到 Telegram。
門檻該怎麼設請一併說明理由。
可以參考 templates/telegram-bot/ 的做法。
```

## 四、作廢與折讓（14–17）

**14. 開錯了怎麼辦**
```
我剛剛開了一張發票，統編打錯了。
請說明「作廢後重開」與「註銷重開 VoidWithReIssue」的差別，
哪一種比較安全、為什麼，以及各自的期限限制。
```

**15. 部分退貨**
```
客人買了三件退了一件，要開折讓。
請說明歐付寶 B2C 的 Allowance（紙本開立）與 AllowanceByCollegiate（線上通知開立）差在哪，
我這個情境該用哪一個，以及選錯會發生什麼事。
```

**16. 折讓也開錯了**
```
折讓單開錯金額了。
請說明 AllowanceInvalid 與 AllowanceInvalidByCollegiate 的使用時機與差別，
並提醒我這個動作是不是可逆的。
```

**17. 二次確認機制**
```
作廢和折讓都不可復原，我想在後台加二次確認。
請設計一個流程：操作者送出 → 系統顯示影響範圍 → 輸入驗證碼確認 → 執行 → 寫稽核 log。
UI 的部分請遵循 docs/accessibility.md 的無障礙要求。
```

## 五、B2B（18–21）

**18. 存證還是交換**
```
我們要開 B2B 發票給企業客戶。
請說明 ExchangeMode 的存證模式與交換模式差在哪，
我怎麼判斷該用哪一種，以及選錯的後果。
```

**19. 交換模式的完整實作**
```
我要實作 B2B 交換模式。
請列出所有「動作 → 確認」的成對 API，
並畫一張狀態機圖說明發票會經過哪些狀態。
最後請告訴我：只做開立不做確認，會發生什麼事。
```

**20. 買方退回**
```
B2B 的買方把我開的發票退回了。
請說明 Reject 與 RejectConfirm 的流程，
我方系統應該怎麼處理這個狀態，以及要不要重新開立。
```

**21. B2B 查詢與對帳**
```
請整理歐付寶 B2B 的所有查詢 API（GetIssue、GetIssueConfirm、GetInvalid… 等），
說明每一支的用途，並設計一個每日對帳流程：
用哪幾支 API、比對什麼、發現差異怎麼處理。
```

## 六、離線發票（22–24）

**22. 我需要離線發票嗎**
```
我們是實體門市，網路偶爾會斷。
請說明歐付寶離線電子發票的適用情境，
以及它與一般 B2C 開立在流程上的關鍵差異。
如果我的門市網路其實很穩，還需要它嗎？
```

**23. 取號策略**
```
離線發票有三種取號方式：
GetOfflineInvoiceWordSettingWithAutoSplit、GetOfflineInvoiceWordSetting、
GetOfflineInvoiceWordSettingNumber。
請說明三者的差別，以及多台 POS 機的情境下該用哪一種、每次該取多少張。
```

**24. 上傳期限**
```
離線發票開立後要上傳。
請說明 OfflineIssue 與 OfflineInvalid 的用法、上傳期限，
以及「機台離線超過期限」時我該怎麼設計告警。
```

## 七、後端整合（25–27）

**25. FastAPI 整合**
```
請依 guides/19-backend-fastapi.md，
幫我設計一個 FastAPI 的發票服務模組：
路由設計、背景任務、資料庫 schema（含冪等鍵與稽核 log）、
以及錯誤處理策略。程式碼請可直接執行。
```

**26. Laravel 整合**
```
我們是 Laravel 專案。
請依 guides/21-backend-php.md，設計歐付寶電子發票的整合：
Service class、Queue job、Migration、以及設定檔該怎麼放金鑰。
```

**27. 冪等性設計**
```
呼叫 Issue 逾時了，我不知道發票有沒有開出來。
請設計一套完整的冪等性機制：冪等鍵怎麼產生、存哪裡、
逾時後的查詢流程、什麼情況才可以重送。
並明確告訴我哪些 API 可以安全重試、哪些絕對不行。
```

## 八、除錯與維運（28–30）

**28. 加密驗不過**
```
我的加密結果和 test-vectors 裡的官方向量不一樣。
請依 references/urlencode-table.md 與 references/encryption-aes.md，
列出可能的原因並排序（機率高的在前），
每一項給我一個可以立刻執行的檢查方式。
```

**29. 看不懂的錯誤**
```
我呼叫 /B2CInvoice/Issue 得到 TransCode=0，訊息是「<脫敏後的錯誤訊息>」。
請依 references/error-handling.md 分析可能原因，
並告訴我該按什麼順序檢查。
（我的金鑰與發票資料已脫敏，不會貼上來。）
```

**30. 上線前檢查**
```
我下週要把歐付寶電子發票推上正式環境。
請依 guides/24-prod-monitoring.md 與 SECURITY.md，
產出一份上線前檢查清單，分成「金鑰與安全」「環境設定」「程式邏輯」「監控告警」四類，
每一項要能用 yes/no 回答。
```

## 進階：讓 AI 自我檢查

在任何回答之後追加這句，可以有效抓出幻覺：

```
請逐條標註你剛才回答中的每個欄位名稱與規則，
出自 references/ 的哪一個檔案、哪一節。
若有任何一項你無法在檔案中找到出處，請明確說「這一項我不確定」。
```

還有這句，用來防止 AI 把綠界的做法混進來：

```
請確認你剛才的回答中沒有出現 CheckMacValue、SHA256、MD5 這些字眼。
歐付寶電子發票用的是 AES-128-CBC 加密整包 Data，沒有 CheckMacValue 欄位。
如果有出現，請重新回答。
```

## 不要這樣問

| ❌ 不好的提問 | 為什麼 | ✅ 改成 |
|---|---|---|
| 「幫我串電子發票」 | 沒說哪一家、哪一類 | 「幫我串**歐付寶 B2C** 開立發票」 |
| 「這段程式碼哪裡錯」＋貼上含金鑰的程式 | 洩漏金鑰 | 金鑰先換成 `<REDACTED>` 再貼 |
| 「發票開不出來」 | 沒有錯誤碼、沒有情境 | 「`TransCode=0`，訊息是…，我的檢查是…」 |
| 「直接幫我打正式環境測試」 | 會產生真發票 | 「幫我在**測試環境**驗證」 |
| 「這樣寫合法嗎」 | 本 Skill 不提供法律意見 | 「規格上這樣填對嗎」＋另外諮詢會計師 |
