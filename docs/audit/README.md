# 獨立稽核紀錄（Independent Audit）

> 這個資料夾存放的是**針對本 repo 的稽核報告**，不是本 repo 的自我宣稱。

## 為什麼要有這個資料夾

本 Skill 的核心承諾是「歐付寶三份官方技術文件裡的**每一個功能**都被完整寫出來，一支都不漏」。

問題是：**「我檢查過了，沒有漏」這句話本身沒有價值。** 寫的人和檢查的人是同一個，就只是自己蓋章給自己。所以本 repo 的完整性由三層互相獨立的機制把關：

| 層級 | 機制 | 位置 |
|---|---|---|
| 1. 機器關卡 | 12 道 CI validator，任一紅燈即擋下 PR。每支腳本的第一個檢查都是「我確實掃到東西了」——一個掃不到任何檔案的守門腳本會永遠是綠的，那比沒有這道關卡更糟 | [`../../scripts/`](../../scripts/) |
| 2. SSOT 對帳 | `validate-api-coverage.sh` 以 [`api-coverage.json`](../../references/api-coverage.json) 為準，逐支比對 reference／guide／三語言 client，並做**反向檢查**（reference 裡出現但沒登記進 SSOT 的 endpoint 也會紅燈） | [`../../scripts/validate-api-coverage.sh`](../../scripts/validate-api-coverage.sh) |
| 3. **獨立稽核** | 由**未參與撰寫**的稽核者，**不採信 repo 內任何自述與 coverage 清單**，直接從官方文件原文重新建立功能清單，再回頭比對 repo 缺了什麼 | 本資料夾 |

第 3 層是這個資料夾存在的理由：機器關卡只能驗證「清單上的東西都在」，驗證不了「清單本身有沒有漏」。稽核者的任務是**證明撰寫者漏了東西**，不是幫他背書。

### 稽核發現的 6 項缺失（全數已修正）

稽核不是走過場。以下每一項都是稽核者附上**官方原文行號**指出來的，全部已在 commit 中修掉：

1. **`b2c-api-reference.md` 未收錄 i100 的 Version History 表**（原文第 41–49 行，7 列）。這是「哪些欄位／章節是新增的」的唯一權威索引 —— 例如 `ZeroTaxRateReason` 是 V1.5.0 才加的，舊系統升級最需要這張表。證明是疏漏而非設計選擇：離線 reference 有這張表，三份處理方式不一致。→ **已補**
2. **`b2b-api-reference.md` 完全沒轉寫 i200 §1／§2／Version History**，導致**平台商測試金鑰**（`PlatformID 2046611` / HashKey / HashIV）、財政部「授權歐付寶」與「接收設定」、字軌四步驟、官方操作手冊連結全部缺席 —— 而 B2B 的 27 支 API 每一支都用 `PlatformID`。→ **已補**
3. **`b2b-api-reference.md` 有一句可被證偽的斷言**：宣稱附錄 3 的解密範例 (3) 「原文在此行後即結束、未擷取到」。實際上原文**確實有**該行（末行無換行字元導致 `wc -l` 少算一行）。內容猜對了不影響串接，但這種斷言直接打到「只照抄、不編造」這個賣點的根。→ **已改為逐字照抄**
4. **`enums.md` 對離線文件的 `CarrierType` 描述與原文相反** —— 寫「i301 只寫空字串、其餘比照 i100」，但 i301 原文第 887 行白紙黑字列了 `1`~`8` 全部載具類別。→ **已更正，並補上來源註記**
5. **B2C 測試環境參數表漏了原文 2 列**（身分證件末四碼／統一編號、平台商子廠商設定說明）。→ **已補，並標註原文中兩個 PlatformID 並存的矛盾**
6. **原文自身的跨章矛盾未標註**：`TaxType` 在 `Issue`（原文 392 行）與 `DelayIssue`（575 行）寫「`InvType=07` 填 1、2、3 或 9」，但 `VoidWithReIssue`（1428 行）只寫「1、2 或 9」，少了 `3`（免稅）。逐字照抄是對的，但沒標註會讓人誤以為免稅發票不能註銷重開。→ **已在兩處加上 ⚠️ 並註明原文行號**

### 稽核明確聲明「未涵蓋」的範圍

誠實的稽核要說清楚自己沒看什麼，否則讀者會過度推論：

- 官方文件中以**圖片**呈現的內容（情境流程圖、錯誤代碼後台截圖、離線附錄 1 交易狀態代碼表）無法從文件的純文字內容取得，稽核只能確認 repo 的**標註是誠實的**（照實說明無法轉寫、未自行編造代碼），無法驗證圖片內容本身。
- 三語言 client 的 **65 個方法參數逐一比對**未執行，只比對了 endpoint 路徑覆蓋。
- 兩份報告的範圍互斥：B2C 稽核者未驗證 B2B／離線，反之亦然。

## 這個 repo 對錯誤的態度

官方文件本身有瑕疵（範例 JSON 少逗號、欄位表拼字錯誤、型態與範例值不符、跨章矛盾）。本 repo 的處理原則是：

> **逐字照抄，加 `⚠️` 標註，不「順手改對」。**

理由：改對了看起來比較舒服，但讀者會拿本 repo 去和官方文件對照，發現不一致時無法判斷是誰錯。照抄 + 標註讓兩件事都成立 —— 你知道官方寫了什麼，也知道那裡有坑。

稽核抽查了 15 處原文瑕疵，其中 14 處 repo 已照抄並標註（B2C 側另抽查 8 處 ⚠️ 全部屬實）。

## 關於報告中的「原文第 N 行」

報告引用的行號，指的是**稽核當下把官方技術文件轉為純文字後的檔案**之行號。
該純文字檔與官方文件本身 **均未隨本 repo 發布**（著作權屬歐付寶），因此讀者無法直接以行號覆核。

這是刻意的取捨，也必須誠實說明：

- **保留行號**的理由：稽核者必須提出可回溯的證據，否則報告就只是另一種「我檢查過了」。行號讓撰寫者能立刻驗證每一筆指控。
- **不發布原文**的理由：官方技術文件不是本 repo 可以再散布的內容。本 repo 收錄的是**介接所需的欄位規格與流程**，不是文件本身。

若你要自行覆核：向歐付寶取得官方三份技術文件，以任一文件轉純文字工具處理後，行號即可對應（不同抽取工具可能有 ±數行的偏移）。

## 這份報告不是背書

稽核者明確聲明了自己**沒有**驗證的範圍（見各報告附錄）。特別是：

- 官方文件中以**圖片**呈現的內容無法從純文字取得，稽核只能確認 repo 的標註誠實，無法驗證圖片內容。
- 兩份報告範圍互斥：B2C 稽核者未驗證 B2B／離線，反之亦然。
- 三語言 client 只比對了 endpoint 路徑覆蓋，未逐一比對 65 個方法的參數。

**通過稽核不等於沒有錯。** 它只代表：在稽核者用盡當下可用的比對方法後，找到的問題都已列出並修正。發現新問題請開 issue。
